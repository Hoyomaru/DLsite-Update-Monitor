# Playnite実機スモークテスト

このテストは、GitHub ActionsのCore / Windows Plugin buildが成功した候補commit、または`tools\Validate-Build.ps1`が成功して`artifacts\plugin`を生成した候補commitに対して実行してください。

可能な限り、GitHub Actionsが生成した`DLsiteUpdateMonitor-smoke-<commit SHA>` Artifactをそのまま使ってください。実機で確認したバイナリと最終Release候補を一致させるため、Smoke Test開始後は理由なく再ビルドしません。

初回はPlayniteのバックアップ、または検証用プロファイルの使用を強く推奨します。特にGate Fの孤立データ整理は、削除してよいテスト用ゲームを作れる検証用プロファイルで実施してください。

## Gate A — 読み込みとメニューを確認

1. CI Artifact、`tools\Install-Dev.ps1`、または`artifacts\plugin`を専用の拡張機能フォルダへ配置します。
2. Playniteを起動します。
3. 拡張機能の読み込みエラーが出ないことを確認します。
4. メインメニューに次が表示されることを確認します。
   - `全ゲームを今すぐ確認`
   - `キャッシュを利用して確認`
   - `エラー/要確認のゲームを再確認`
   - `DLsiteリンク診断`
   - `孤立した追跡データを整理`
   - `キャッシュをクリア`
5. ゲーム右クリックメニューに次が表示されることを確認します。
   - `今すぐ確認`
   - `監視詳細を表示`
   - `DLsiteページを開く`
   - `現在の変更を適用済みにする`
   - `現在の変更を無視する`
   - `監視状態をリセット`
6. プラグイン設定を開き、値を変更せず保存します。

**合格条件:** クラッシュ、拡張機能エラー、予期しないゲームメタデータ変更がないこと。

## Gate B — DLsiteリンク診断だけを実行

1. `DLsiteリンク診断`を実行します。
2. 正常 / リンクなし / 不正 / 曖昧の件数を確認します。
3. 問題のあるゲームがある場合、ゲーム名と理由が診断詳細に表示されることを確認します。
4. 曖昧なリンクでは候補ProductIdが表示されることを確認します。
5. この段階では更新チェックを実行しません。
6. タイトル、Links、Notes、Sources、ジャンル、既存のユーザータグが変更されていないことを確認します。

**合格条件:** 診断処理が読み取り専用で、問題箇所を特定できること。

## Gate C — 既知の1作品と監視詳細

PlayniteのLinksに有効なDLsite作品URLが登録されているゲームを1本だけ選びます。

1. チェック前に`[DLsite更新]`タグの有無を確認します。
2. `今すぐ確認`を1回実行します。
3. 未追跡のゲームでは結果が**監視開始: 1**になることを確認します。
4. 初回観測で`[DLsite更新] 更新あり`や`[DLsite更新] 配布物変更`が付かないことを確認します。
5. プラグインのユーザーデータフォルダに`tracking.json`が作成されることを確認します。
6. `監視詳細を表示`を開き、少なくとも次を確認します。
   - 状態が`変更なし`
   - 最終チェックが`正常`
   - ProductIdが対象作品と一致する
   - `確認済み基準`が存在する
   - `現在の比較可能状態`が存在する
   - `直近の観測`が存在する
   - 初回 / 最終試行 / 最終成功時刻が不自然でない
7. `tracking.json`でも次を確認します。
   - `AcknowledgedSnapshot`が存在する
   - `CurrentSnapshot`が存在する
   - 両者のフィンガープリントが一致する
   - `MonitoringState`が`Clean`
   - `LastCheckHealth`が`Healthy`
8. 状態を変更せず、同じゲームで`今すぐ確認`をもう一度実行します。
9. 更新タグが付かず、状態が`Clean`のままであることを確認します。

**合格条件:** 初回観測はベースライン作成だけで、同一状態の2回目チェックも変更なしになること。監視詳細が保存状態と一致すること。

## Gate D — エラー時の安全性と再確認

まず、一時的な通信失敗や不正リンクが既存状態を壊さないことを確認します。

1. テスト用ゲーム、または復元可能な状態でDLsiteリンクを一時的に不正なURLへ変更します。
2. チェックを実行します。
3. `LinkError`または要確認エラーとして扱われることを確認します。
4. `監視詳細を表示`し、既存の確認済み基準 / Currentが消えていないことを確認します。
5. 正しいリンクへ戻します。
6. メインメニューの`エラー/要確認のゲームを再確認`を実行します。
7. 対象ゲームだけが再確認され、正常状態へ戻ることを確認します。
8. 既存の`AcknowledgedSnapshot`と`CurrentSnapshot`が維持され、「監視開始」へ戻っていないことを確認します。

保留中の更新状態を用意できる場合は、その状態でもエラーチェックを行い、保留状態が維持されることを確認してください。

### HTTPリンクのHTTPS正規化

復元可能なテスト用ゲームで、正しいDLsite作品URLのschemeだけを`http://`へ変更します。

1. `DLsiteページを開く`またはチェックを実行します。
2. Plugin内部ではHTTPS URLとして扱われることを確認します。
3. trackingの`RegisteredUrl`がHTTPSになっていることを確認します。

`ftp:`などHTTP(S)以外のschemeは有効なDLsite作品URLとして受け入れられないことも確認します。

### 作品ID変更の安全性

1. 追跡済みゲームの現在の作品IDを記録します。
2. PlayniteのDLsiteリンクだけを、**別の有効な作品ID**へ変更します。
3. `今すぐ確認`を実行します。
4. プラグインが`LinkError`で停止し、新しい作品に古いベースラインを流用しないことを確認します。
5. `監視状態をリセット`を実行します。
6. もう一度チェックし、新しい作品が新規ベースラインとして受け入れられることを確認します。

利用停止・販売終了などのDLsite作品で、HTTP 200のエラーページが返るケースを確認できる場合は、一般的な解析エラーではなく`ProductUnavailable`として扱われることも確認します。

**合格条件:** 取得失敗で有効なベースラインや保留状態が消えず、作品IDが暗黙に切り替わらず、対象エラーだけを再確認できること。

## Gate E — タグと状態操作

1. 検証用ゲームにユーザータグ`[DLsite更新] 自分用メモ`を手動で作成・付与します。
2. 設定の`更新状態をPlayniteタグへ反映`をOFF→ONしても、そのユーザータグが削除されないことを確認します。
3. Pending状態を再現できる作品がある場合、状態とタグが一致することを確認します。
   - 更新情報のみ → `[DLsite更新] 更新あり`
   - 配布物のみ → `[DLsite更新] 配布物変更`
   - 両方 → **2つのタグが両方付く**
4. 両方変更を再現できる場合、チェック結果サマリーの`更新あり`と`配布物変更`の双方へ含まれ、`両方変更`にも計上されることを確認します。
5. `現在の変更を適用済みにする`または`現在の変更を無視する`を実行し、状態が`Clean`へ進みPlugin管理タグが消えることを確認します。
6. `監視状態をリセット`を実行し、次回チェックが新規Baseline扱いになることを確認します。

**合格条件:** Plugin所有の2タグだけを管理し、同じprefixのユーザータグを壊さず、Combined stateを2つの変更軸として表示できること。

## Gate F — 孤立した追跡データ整理

**このGateは削除してよいテスト用ゲームを使える検証用Playniteプロファイルで実行してください。**

1. テスト用ゲームを作成し、有効なDLsiteリンクを登録してBaselineを作成します。
2. `tracking.json`からそのゲームのGameId / ProductIdが記録されていることを確認します。
3. Playniteからそのテスト用ゲームを削除します。
4. `孤立した追跡データを整理`を実行します。
5. 削除候補件数、ProductId、GameIdが確認ダイアログに表示されることを確認します。
6. 一度`No`を選び、`tracking.json`から記録が消えていないことを確認します。
7. もう一度実行して`Yes`を選びます。
8. `tracking.json`から削除済みゲームのrecordだけが消え、現在存在するゲームのrecordが残ることを確認します。
9. 現在存在するゲームのタグやメタデータが変更されていないことを確認します。

**合格条件:** Previewと明示確認が機能し、孤立recordだけを安全に削除できること。

## Gate G — 小規模バッチ、再起動、全ライブラリ

1. 有効なDLsiteリンクを持つゲームを5〜10本選びます。
2. `今すぐ確認`を実行します。
3. 進捗表示とキャンセル操作が応答することを確認します。
4. 新規ゲームは更新通知ではなくベースライン作成になることを確認します。
5. 同じ作品IDを意図的に参照するゲームが複数ある場合、そのバッチ内ではリモート観測が再利用されることを確認します。
6. Playniteを再起動し、保存した監視状態が再読み込みされることを確認します。
7. 設定の`更新状態をPlayniteタグへ反映`を一時的に無効にします。
8. Plugin管理の2タグだけが消え、無関係なユーザータグが残ることを確認します。
9. タグ連携を再度有効にし、保留状態に対応するタグが復元されることを確認します。
10. Playniteをバックアップします。
11. 全ライブラリチェックを実行します。
12. `エラー/要確認`と診断詳細を確認してから更新タグを判断します。
13. 結果が妥当であることを確認します。

**合格条件:** 永続状態が正しく復元され、タグ連携を安全にON/OFFでき、全ライブラリでも大量の誤検知が発生しないこと。

`.pext`の作成・配布は、Gate A〜Gが成功したあとに行ってください。

## 即時中止条件

次のいずれかが起きた場合はテストを中止し、`tracking.json`、`tracking.backup.json`、Playniteログ、問題が起きたDLsite URL、使用したcommit SHAを保存してください。

- 初回チェックで更新タグが付く
- 403 / 429 / timeoutによって保留状態が消える
- パーサー失敗で既知のスナップショットが上書きされる
- 保存失敗表示後の操作が、後の保存で勝手に確定する
- backupから復旧したあと正常backupが失われる
- Plugin管理外のタグが削除される
- 孤立データ整理で現存ゲームのrecordが削除される
- Notes / Links / タイトルが変更される
- 無関係な多数のゲームが同時に更新扱いになる
